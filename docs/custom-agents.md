# API Agent 的配置与协作

Lemma 的 API 成员与 CLI 成员使用相同的任务、会话和结果管理流程。成员按职责配置，模型与服务地址决定执行方式；同一模型可以承担多个独立成员。

当前版本以 coding 协作为主：API 成员同样可以承担编码、测试、仓库分析和代码审查。文中的通用配置说明描述已有接入能力；其他领域及面向其他开发者的单独适配属于后续工作，不作为当前版本的设计目标。

## 配置与启动

运行 `npm start`，用 `/setup` 引导配置总控，用 `/agent add` 引导添加成员：依次输入成员 ID、名称、职责、专属指令、API 协议、服务地址、模型、工作区与工具权限，最后隐藏输入 API 密钥。已有配置会继续加载，也可用 `PI_AGENT_CONFIG` 指定其他配置文件。

`/agent edit <ID>` 修改 API 成员；`/agent enable|disable <ID>` 启停成员；`/agent model <ID> [模型ID]` 修改默认模型；`/agent key <ID>` 隐藏输入密钥；`/agent show <ID>` 查看配置；`/help` 查看命令。CLI 成员沿用自己的登录，目前支持在终端启停和修改默认模型。

表单输入是本地配置操作，不发送给模型，不加入聊天历史。Enter 确认字段，留空保留当前值；Esc 或 Ctrl+C 取消。配置只在各工作会话都空闲时修改，保存后同步现有工作会话；已运行的成员上下文、数据库与结果保持。启停和配置操作本身不测试服务、不产生模型请求，随后派工才按实际服务计费。

密钥可继续通过配置的环境变量提供，也可以在向导中输入并保存到本机 `~/.lemma/credentials.json`。配置文件仅保存 `credential` 引用，设置本机凭据后该成员使用本机凭据；文件是明文存储，POSIX 下限制文件权限，Windows 下仍需保护用户目录权限。它不属于项目仓库或会话数据库，换机器须重新配置凭据。`LEMMA_CREDENTIALS_FILE` 可显式更换本机存储位置。密钥不写入角色指令、网页响应或模型上下文。

终端与本地管理网页一起启动；`/agents` 查看角色和模型，`/members` 查看成员上下文，Ctrl+K 可只读浏览 API 子对话，`/tasks`、`/jobs` 沿用原有管理命令。网页“成员会话”、成员卡片、派工筛选、统计和拓扑支持自定义成员。网页仍不直接下发任务。

## 如何协作

1. 向总控说明目标、必要资料、约束与验收标准。简单任务可以直接完成；需要分工时，按职责选择成员。
2. 独立任务可同轮并行或放到后台；有依赖的任务由总控在前置结果到齐后继续派发。分工表用于记录依赖，不会自动调度所有节点。
3. 成员在独立会话中处理明确交付的任务，返回报告与结果引用。总控按需读取全文，将下一步所需的证据交给后续成员。
4. 同一工作的追问传回原 `session_id`，只补充变更；独立工作创建新会话，避免无关历史混入。
5. 总控根据验收标准检查结果，记录待验收、完成或受阻状态；需要时继续派工或交给用户判断。运行过程中可以查看进度、取消任务，重启后可恢复对应会话。

默认成员只接收任务里明确交付的资料，不自动读取电脑里的文档，也不复制总控整段聊天。需要读取本地文件时，可给对应成员配置 `api.tools: ["read"]`，并在任务里交付相对路径。

## 成员配置

`agents` 的键是成员 ID，可以使用小写字母开头，后接小写字母、数字或下划线，最多 48 个字符；系统保留名不能使用。它用于任务、会话和历史记录，已运行后不建议随意重命名。

| 字段 | 含义 |
|---|---|
| `name` | 终端与网页显示的角色名称 |
| `description` | 总控据此选择成员，说明适合处理的任务 |
| `instructions` | 该成员专属指令，进入它自己的系统上下文 |
| `models` / `defaultModel` | 允许使用的模型与默认模型；API 成员未指定默认时取清单第一项 |
| `api.type` | `openai-compatible` 或 `anthropic-compatible` |
| `api.baseUrl` | 对应协议的服务地址；不能在 URL 中放用户名或密码 |
| `api.apiKeyEnv` | 按顺序读取凭据的环境变量名 |
| `api.credential` | 终端自动保存的本机凭据引用；不是密钥原文 |
| `api.tools` | 显式授予 `read`、`write`、`edit`、`bash` 中的工具；自定义成员默认 `[]` |
| `api.httpTools` | 仅授权给该成员的 HTTP 业务工具；固定端点、参数 JSON Schema、GET/POST 与凭据引用 |
| `api.bash` / `bashAllow` | shell 的额外开关和命令白名单；默认关闭，即使列入 tools 也要明确开启 |
| `workspace` | `none`：领域对话/工具协作；`code`：已有代码工作区流程 |
| `timeoutMinutes` / `api.maxTurns` | 单次派工超时、最多工具轮数 |
| `maxOutputChars` | 自动回传的预览长度；全文另行持久保存 |
| `models[].price` | 每百万 token 的价格，只有配置或服务报告时才能可靠统计费用 |

`collaboration.instructions` 为总控、子调度及 API 成员提供共同领域说明；`roles` 将业务岗位映射到成员 ID。纯非代码团队没有配置 roles 时，不自动套用默认编码角色表；混合团队保留原有默认角色，也可显式配置 `roles` 或设为 `[]`。

同一模型可以承担多个 Agent：每个成员有自己的 provider 注册名、系统指令、工具权限和独立会话。不同成员也可以配置不同服务地址、凭据、协议与模型，混合使用。新成员使用 `ask_<成员ID>` 工具（例如 `ask_analyst`），沿用同步、同轮并行和 `background: true` 的已有派工方式。

## 工作区与兼容性

- 自定义 API 成员默认 `workspace: "none"`：不创建 worktree、不执行 Git 快照与提交、不运行代码检查/自动代码修复，也不装入编码规范或编码修复经验。即使全局打开代码隔离/代码验收，这些成员也不会套用它们。
- `workspace: "none"` 的成员拒绝 `based_on`。跨成员交接应传必要资料与结果片段；总控可用 `read_result` 取回省略证据，再交付给下一成员。
- 显式开启文件写入并不提供文件系统隔离；非代码成员的文件工具作用于配置工作目录，可能修改原文件。文件路径访问沿用既有检查，shell 权限沿用既有白名单机制，不等于 OS 沙箱。
- 旧的 `claude`、`codex`、`gemini`、`deepseek` 配置继续加载，默认保留 `workspace: "code"` 和原有权限约定。自定义 API 成员也可显式选择 code；内置 CLI 暂不提供非代码执行模式。
- 没有启用的成员不会启动。演示模式会禁用自定义真实 API 成员，只运行已有模拟剧本，避免误请求。

## 会话与任务闭环

每次新派工在 Durable 中创建任务拥有的独立 API 子对话，返回 `session_id`；同一工作的增量追问传回该 ID。成员与总控归属检查、预算、超时、取消、后台任务和重启恢复沿用同一条执行链路。重启不会另建一套会话系统；未完成的 API 派工通过任务所有权与幂等 requestId 找回，已完成记录不丢。

总控收到限长报告与 `result_id`，通过 `read_result` 分页读取原文，完整聊天仍在成员子对话中。域内任务也支持 `plan_tasks → ask_* → wait_jobs → update_task`；成员成功返回只代表执行完成，任务先进入待验收，由总控根据验收标准核对。

任务可以在 `plan_tasks` 中预设 `checks`：`contains` 检查报告全文包含文本；`json_exists` 检查完整 JSON 报告的点分字段路径；`json_equals` 将字段与 JSON 文本解析后的值比较。`value` 在 contains 中是文本，在 json_equals 中是 JSON 文本（例如字符串需带 JSON 引号）。这些规则验证结构与明确字段，不能证明业务事实、审批有效性或资料真实性；仍需总控、复核成员或人工核对依据。

成员返回后自动对**完整结果**计算机器检查，任务保持待验收。`review_task` 用最新 `result_id` 执行 `check`、`accept`、`rework` 或 `block`；除 check 外必须提供 evidence。accept 需要成功执行、规则通过且依赖任务均已验收。首次派工后锁定验收标准；不能通过降低标准、验收旧结果或直接 update_task done 绕过机器规则。返工记录缺口并退回待办，由总控决定是否续接原 session_id，不会无限自动重试。

所有任务均使用相同的完成检查：即使没有机器规则，也必须有成功的最新交付与非空验收依据。兼容的 `update_task status=done` 入口仅用于无机器规则的任务，同样记录正式验收结果；有机器规则时走 `review_task`。进行中和待验收由真实派工产生，运行时不能手动改状态绕过收尾；上级任务完成前，其未取消的子任务也必须完成验收。已经存在的历史完成记录不会自动改写，重新操作时执行新规则。

派工收尾将结果全文及回执、任务状态及最新结果、成员会话轮次、已知费用放在同一 Durable 事务中。执行结果先记检查点；事务前中断会复用检查点，事务提交后中断直接返回已存回执，避免再次调用成员或重复计费。ASSIGN.md 是数据库状态的导出，写入失败不回滚任务、不重新调用成员；重启会尝试重新导出。Git worktree/提交和远端业务服务不属于 SQLite 事务，外部副作用仍需各自的恢复与幂等保障。

跨成员交接支持 `ask_*` 的 `inputs: [{ result_id, field?, offset?, limit? }]`，从同一总控的结果存储中直接提取原文或指定结构化字段和来源；每次最多 8 个片段，每片最多 8000 字符，默认 2000。无需手工复制成员整段聊天。存在 deps 的任务须等前置任务完成验收后才可派工。

`structured: true` 要求成员输出 `lemma.delivery.v1` JSON，包含 `conclusion`、可选 `data`、`evidence: [{ source, excerpt? }]`、`artifacts: [{ path, description? }]` 和 `incomplete: []`。格式无效会保留失败结果，不能直接验收。`read_result` 的 `field: "data.total"`、`ask_*` 的 `inputs[].field` 与 `/result <ID> data.total` 都按相同规则读取；分页明确返回 `nextOffset`。字段过滤避免将其他内容带给下个成员，原文不删除。来源和产物引用仍需核验，格式合法不等于业务真实。

`/tasks`、网页看板与 ASSIGN.md 显示最新结果、机器检查与复核证据；`/result <result_id> [偏移]` 在终端直接分页查看全文，不调用模型。执行异常、超时及取消保留已有成员会话；正常收尾会保存失败结果，失败受阻、取消退回待办。进程关闭和崩溃继续由 Durable 原有恢复路径管理。代码验收与有限代码修复仍保留，业务验收不能绕过已有代码检查。预算按已报告或配置定价的花费执行，缺少价格/usage 时不能视为完整成本上限。

## 在终端接入业务工具

启动 `npm start` 后输入 `/tool add <成员ID> [工具ID]`。向导填写用途、固定 HTTP(S) 地址、GET/POST、参数 JSON Schema；POST 可配置**服务实际支持**的幂等请求头，最后隐藏输入可选 Bearer 密钥。无需先写适配器代码，模型只填写业务参数，不选择地址或认证头。`/tool list`、`/tool edit`、`/tool key`、`/tool remove` 均带成员 ID，后三者再带工具 ID。工具配置在空闲时生效，移除授权保留历史。

GET 将简单字段编码为查询参数；POST 发送 JSON 对象。凭据支持环境变量或本机凭据引用；响应中出现相同凭据原文时会脱敏。请求跟随任务取消，超时默认 30 秒，不跟随重定向；响应超过 128 KiB 返回错误，交给模型的文本默认最多 8000 字符，超出会明确标识截断。工具访问固定配置地址；配置本地/内网接口即表示允许该成员调用该接口。

GET 可在进程恢复时重放；未配置幂等支持的 POST 使用 Durable 原生 replay=unsafe，中断后不自动重放；配置幂等请求头时使用稳定的调用标识。POST 超时或断网可能已在远端生效，需要核对远端状态，不能宣称撤销成功。含 POST 工具的成员不进入代码自动重试流程；领域业务返工由总控带依据决定。

业务失败以结构化类别保存：参数无效、认证/权限失败、限流、暂时不可用、明确拒绝、取消、响应无效与远端状态未知。GET 暂时失败标为可重试查询，但不会无限自动重试；存在 Retry-After 时保存等待时间，冷却期间的新请求会被拦截。POST 在发送后遇到断网、取消、超时、408 或服务端错误时保守记为未知，不能当作确定未执行。

每次 HTTP 请求会先在同一工作会话的 Durable 操作账本中保存意图；参数只记哈希，不保存第二份原始业务参数。`/operations` 查看状态、失败类别、等待时间和人工核对记录。存在 pending/unknown POST 的固定端点会拦截该会话内其他成员发往同一端点的新 POST，且重启保留拦截；配置了幂等支持的**原调用恢复**可沿用原幂等键。该保护不跨独立顶层会话/数据库，也不能识别不同 URL 背后实际指向同一业务操作的情况。

查询远端业务流水后，用户可在空闲终端输入 `/operations resolve <ID> succeeded <依据>` 或 `/operations resolve <ID> not_applied <依据>`。仅用户本地命令能解除未知状态，模型没有相应工具；命令只保存查询结论，不调用远端、不撤销操作，也不将原失败报告改为成功。确认未执行后可重新派工；确认已成功后拦截同一端点相同参数的再次提交，并应基于远端凭证继续验收。网页看板也会列出待核对操作，不显示认证信息或请求体。

## 当前范围

### 受阻任务恢复

`/task inspect <ID>` 查看最近派工、失败结果引用、验收缺口、恢复计划和可复用的已验收前置结果。`/task resume <ID> <依据>` 续接原成员会话；`/task supply <ID> <资料>` 保留新增资料并续接，无法续接时新建该成员会话；`/task reassign <ID> <成员ID> <依据>` 新建其他成员会话并附历史交付节选、原结果引用、复核缺口与新增资料。已有代码改动通过 `based_on` 继承，不从主目录静默重做；原会话默认沿用仍可用的原模型。原验收标准与 checks 保持锁定，已验收依赖不重新执行。

终端恢复直接建立原生 Durable 后台任务，不需要额外总控请求转述指令；结果回到所属总控正常验收。`/jobs cancel <Jn>` 停止运行或排队的恢复派工；`/task cancel <ID> <原因>` 只撤销模型准备但尚未执行的恢复计划。`recover_task` 为总控提供 inspect/resume/supply/reassign/cancel，返回明确成员及 dispatch 参数供 `ask_*` 使用；计划持久化并防止重复派工。模型不能通过恢复绕过未核对的 POST、其他总控的成员会话、待验收或已完成任务。旧记录缺少 lastAttempt 时不推测归属，保留原显式 session_id 续接方式。

### 上下文与派工

新派工默认只带当前任务、直接前置、上级和直接后续分工，其他任务不夹带。成员续接按相同项目背景、结果 ID、字段与片段内容指纹省略重复文本；只复用当前成员会话实际收到的相同片段。资料变更会重发；API 会话原生 reset 或压缩的 head 变化会使复用失效。可用 `context_mode: "full"` 强制重发相关背景与显式资料；CLI 内部压缩不可观测，认为资料不足时应强制 full。完整历史及结果不删除，也不在成员间共享聊天。

总控系统规则要求先判断是否需要分工，优先复用当前任务已验收成果，字段按需交接。独立核查、资料过期或来源冲突仍应重新查证；没有全局缓存自动替代业务查询，也没有基于未运行真实评测的自动模型路由。测试验证真实发送的任务文本与状态约束，不能代替真实模型遵循率和成本评测。

本次交付：任意 API 成员 ID、角色指令、两类已有 API 协议、显式文件/shell 工具授权、非代码执行路径、现有界面的动态成员目录，以及并行、后台、隔离、续接、取消和进程恢复。

HTTP 向导的参数步骤可输入 `fields`，逐个填写名称、基础类型、说明和必填项；复杂参数仍可填写完整 JSON Schema。`/tool test <成员> <工具>` 仅对已授权 GET 发真实请求并验证参数，不调用模型；POST 不提供测试入口，避免产生重复业务操作。

MCP 使用固定版本官方 SDK 的 Streamable HTTP 客户端：`/mcp add <成员> <连接ID>` 填地址和可选 Bearer 密钥，发现分页工具目录后，明确选择工具名称；`/mcp list|refresh|remove <成员> [连接ID]` 查看、重新授权或移除。仅接受服务明确标记 `readOnlyHint: true` 的工具，工具权限按成员隔离，每次调用重新核对整个分页目录与参数 Schema。工具定义发生变化时停止调用并要求 refresh；对象键顺序变化不会误报。只读标记是服务的声明，不是沙箱保证，请只授权可信服务。

`/limits` 查看、`/limits edit` 配置并发与预算：团队默认 8、每成员 4、每服务 8；同一模型 API origin 共享服务名额，CLI 按成员计。名额与队列在 Durable 事务内准入，等待使用原生挂起，重启可恢复；取消和结束释放预留。`budget.reservePerDispatchUsd` 默认 0；设置后，新派工按已知花费加运行中预留核对余额。预留不是实际费用，返工仍计费，缺少 usage 或价格时不能保证账单上限。范围是单个工作会话数据库，不是跨进程或跨会话全局限流。`/progress` 和网页查看等待，`/usage` 查看成员/返工已知费用及未知次数，总控与子调度仍按模型汇总。

当前还不支持 MCP 写操作、stdio、OAuth 流程、任意自定义认证头、单个 Agent 内部的多模型工作流，以及判断所有行业事实的自动验收器。外部 POST 不提供跨系统事务或自动回滚；行业数据源、业务规则与远端幂等能力仍由实际服务提供。

测试：`npm run test:custom-agents`。测试使用本机固定响应 HTTP 服务，实际走现有模型协议适配器、Durable 与应用宿主；不请求真实模型、不产生服务费用，不等于行业输出质量评测。

业务工具与验收回归：`npm run test:business`；终端配置回归：`npm run test:settings`。覆盖原生 Durable 调用 HTTP、权限与密钥、失败/取消/超时、规则锁定、旧结果拒绝、明确返工与原文交接。

`test:business` 还覆盖收尾执行检查点后、事务内与事务提交后，以及返工结果提交后、完整返工回执保存后共五处强杀进程，验证恢复不重复执行、计费或累计会话轮次，保留最终返工交付；以及未知写操作跨成员/重启拦截、人工核对、确认成功防重与限流冷却。

`npm run test:collaboration` 覆盖依赖就绪推进、独立复核、有限返工、暂停与恢复、字段交接、同步/后台队列、预算预留、重启恢复、单独取消、同服务并发限制、MCP 分页发现与授权变更，以及完整任务对照的成功和失败计分。`npm run bench:collaboration` 生成本地固定响应基线；显式 `--real` 才调用真实模型，模拟模式不报告真实成本或 token 收益。

### 依赖推进与独立复核

`plan_tasks` 每项可选 `automation: { member: "researcher", model: "已配置模型ID", maxReworks: 1 }` 与 `reviewer: { member: "checker" }`。未声明 automation 时不会自动派工；声明 reviewer 后，当前交付必须通过该独立成员复核，不能用 `update_task done` 绕过。复核成员与执行者必须不同，复核会开启独立上下文，不继承执行者聊天。API 复核成员使用专用只读配置（`tools: []` 或 `["read"]`、`bash: "off"`，HTTP 仅 GET）；CLI 成员继续遵循现有隔离约束，指令要求只读，发现复核分支产生提交改动时拒绝通过，这不构成操作系统沙箱。

复核结果格式为 `{"verdict":"accept|rework|block","result_id":"被复核结果ID","evidence":"逐项核对依据或具体缺口"}`。自动复核只接收最多 8000 字符的完整交付，超限会受阻交总控拆分；自动下游最多交接 8 项同总控依赖结果，每项 2000 字符并保留引用和偏移信息。系统不会把被截断的复核输入视为完整验收。代码复核沿用 based_on 创建独立工作副本，实际源码版本变化后旧复核失效。

`/ready` 查看就绪任务与依赖等待；`/workflow status|pause|resume` 查看或暂停恢复自动推进。暂停不取消已有作业，取消作业继续使用 `/jobs cancel <ID>`；失败、取消和未知外部操作不会自动反复重跑。已完成前置任务不随返工重做，所有复核与恢复记录留在当前会话。

单一代码依赖通过 `based_on` 带入已验收分支；多个前置分支由 Durable 创建集成副本，合并并运行 `autonomy.checks`，通过后下游基于该集成提交开工。未配置检查、冲突或检查失败时不会盲目启动下游。也可用 `/integrate create <ID1> <ID2>` 手动启动，`/integrate show <集成ID>` 看证据，`/integrate cancel <集成ID>` 取消；用户 `/apply <集成ID>` 才将整体改动应用到主目录，不自动提交。模型可调用 `integrate_changes` 和 `read_integration wait:true`，等待由 Durable 挂起而非循环询问模型。

同组测试还包含 `test/task-recovery.ts` 与 `test/context-handoff.ts`：准备恢复跨重启、补资料原会话、换人交接、禁止验收旧结果、未知 POST 与总控隔离、终端直接派工和取消；上下文/字段复用、变更重发、强制 full、原生 reset。`test/repair.ts` 验证代码换人继承原分支后有限修复仍正常收尾。
